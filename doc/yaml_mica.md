# The Mica YAML engine (`-Duse_mica`)

`YAML` can run on [Mica](https://github.com/amberframework/mica)'s YAML
parser and emitter instead of libyaml. Mica is written in Crystal, and
nothing links a C YAML library. Existing code keeps working unchanged:
`YAML.parse`, `YAML.parse_all`, `YAML::Serializable`, `from_yaml`,
`to_yaml`, `YAML.build`, `YAML::PullParser`, `YAML::Builder`, `YAML::Nodes`
and `YAML::Schema::Core` keep their API and their results.

```console
$ crystal build -Duse_mica app.cr
$ otool -L app      # or ldd: no libyaml
```

libyaml stays the default. The flag is the same one that selects Mica's
regex engine (`doc/regex_mica.md`): a program built with `-Duse_mica` uses
Mica for both, and links neither PCRE2 nor libyaml.

## How Mica reaches the standard library

- `src/yaml/mica/` is a copy of Mica's YAML pull parser and emitter and the
  parts of `Mica::Core` they use (positions, errors, the work meter, UTF-8
  and byte scanning), generated by `scripts/vendor_mica_yaml.cr` from a
  pinned commit. The script refuses a checkout whose commit or tree hash
  differs from the pins, and records the sha256 of every vendored file in
  `src/yaml/mica/VENDORED.md`. Nothing in that directory is edited by hand.
- The copy lives in `YAML::Mica`, apart from the top-level `Mica` an
  application may require as a shard and apart from `Regex::Mica`
  (`src/regex/mica/`, its own copy at its own pin). The script rewrites
  `module Mica` to `module YAML::Mica` and `::Mica::` to `::YAML::Mica::`.
- Mica's node API (composer, schema, values) is not vendored: the standard
  library's own `YAML::Nodes`, `YAML::Schema::Core` and `YAML::Any` run on
  the pull parser as they do with libyaml.
- Nothing in `src/yaml/mica/` or `src/yaml/mica_engine/` is compiled unless
  `-Duse_mica` is set.

The two classes that touch the engine are selected in
`src/yaml/pull_parser.cr` and `src/yaml/builder.cr`:

| Class | libyaml (default) | `-Duse_mica` |
|---|---|---|
| `YAML::PullParser` | `src/yaml/libyaml/pull_parser.cr` | `src/yaml/mica_engine/pull_parser.cr` on `Mica::YAML::PullParser` |
| `YAML::Builder` | `src/yaml/libyaml/builder.cr` | `src/yaml/mica_engine/builder.cr` on `Mica::YAML::Emitter` |
| `LibYAML` binding | `src/yaml/libyaml/lib_yaml.cr` | not compiled |

## What stays the same

Mica reads in its libyaml dialect, which follows **libyaml 0.2.5** (the
version applications link today): the same events, the same start and end
marks, the same `YAML::ParseException` messages, lines, columns and
context. Mica's differential campaigns compare the two on millions of
generated documents and require zero disagreements (see Mica's
`docs/yaml.md`). The emitter is a port of libyaml 0.2.5's and writes the
same bytes.

- `spec/std/yaml` passes on both engines (457 examples each).
- `YAML.libyaml_version` returns 0.2.5 under `-Duse_mica`: the dialect the
  engine reads, so version checks written for libyaml see that version.
- The pull parser's nesting guard (`max_nesting`) and alias-to-anchor
  guard are the standard library's own and apply on both engines.
- An `IO` with an encoding set receives the builder's output transcoded,
  as with libyaml.

## Differences

- An `IO` source is read to its end before the first event (libyaml reads
  it in chunks). Events, marks and errors are the same; only the moment
  the `IO` is consumed differs.
- A document that holds a syntax error and, later, a byte that is invalid
  UTF-8 or a forbidden control character: libyaml decodes a block ahead
  and reports the invalid byte; Mica reports the error that comes first in
  the document. Both raise `YAML::ParseException`; the message differs.
- libyaml 0.2.6 (2026-11-20) changed two readings that the engine does not
  follow, because it states 0.2.5: `[? ]` (an explicit key closed by the
  end of a flow sequence) fails as in 0.2.5, where 0.2.6 reads a
  single-pair mapping; and 0.2.6's cap of 1,000 nested collections does
  not exist in the engine. The standard library's own `max_nesting` (512)
  stops deep nesting first on both engines.
- `YAML::Builder` raises `YAML::Error` for a scalar, tag or anchor that is
  not valid UTF-8 at the call that passes it. libyaml fails the same way
  for scalars, but leaves an emitter that reports the earlier event again
  on later calls.
- Speed: parsing is 1.6x to 1.8x as fast as on libyaml; `to_yaml` runs
  from 0.86x (a 2.1 MB manifest) to 1.75x (a short lockfile) of libyaml's
  speed (Mica's `docs/benchmarks.md`, "YAML").

## Updating the vendored copy

1. Check out the new Mica commit.
2. Update `PINNED_COMMIT` and `PINNED_TREE` in
   `scripts/vendor_mica_yaml.cr` from `git rev-parse HEAD` and
   `git rev-parse HEAD^{tree}`.
3. `crystal run scripts/vendor_mica_yaml.cr -- path/to/mica`
4. `crystal spec -Duse_mica spec/std/yaml`
