# The Mica regex engine (the default)

`Regex` runs on [Mica](https://github.com/amberframework/mica)'s regex
engine. Mica is written in Crystal: every search runs in time linear in
the haystack under a work allowance, and nothing links a C regex library.
Existing code keeps working unchanged: `Regex`, regex literals, `$~`,
`String#match`, `#gsub`, `#scan`, `#split` and `Regex::MatchData` keep
their API.

```console
$ crystal build app.cr
$ otool -L app      # or ldd: no libpcre2-8
```

## Choosing the engine

| Build | Engine |
|---|---|
| `crystal build app.cr` | Mica |
| `crystal build -Duse_pcre2 app.cr` | PCRE2 (links `libpcre2-8`) |
| `crystal build -Duse_pcre app.cr`, or the env var `USE_PCRE1` set | legacy PCRE (links `libpcre`) |
| `crystal build -Duse_mica app.cr` | Mica; the flag is accepted so build scripts written while Mica was opt-in keep working |

`-Duse_pcre2` wins over `-Duse_pcre`, and either one wins over
`-Duse_mica`. `src/regex/engine.cr` makes the choice for the program, and
`Crystal::Program#uses_mica_regex_engine?` makes the same choice in the
compiler.

Build with `-Duse_pcre2` when a program needs syntax Mica does not run
(lookaround, backreferences and the others listed under "Syntax Mica does
not run"), `MATCH_INVALID_UTF`, or PCRE2's exact behavior on a haystack
with invalid UTF-8. The compiler itself is built on Mica and links no
PCRE2; a program built with `-Duse_pcre2` needs the PCRE2 library where it
is built and where it runs, as every program did before.

Measured on a production Amber V2 app (the Scribe license server, six
interleaved pairs per route): CPU time, memory and latency per request
equal to PCRE2 within the 95% intervals on every route, 370 of 370 specs
on both engines, and a release binary 1.21 times as large (5,018,672
against 4,163,632 bytes).

## How Mica reaches the standard library

The standard library cannot depend on a shard, and Mica (the shard) is
built with the standard library, so the engine is vendored:

- `src/regex/mica/` is a copy of Mica's regex engine and the parts of
  `Mica::Core` it uses (positions, errors, the work meter, UTF-8 and byte
  scanning), generated by `scripts/vendor_mica.cr` from a pinned release.
  The script refuses a checkout whose commit or tree hash differs from the
  pins, and records the sha256 of every vendored file in
  `src/regex/mica/VENDORED.md`. Nothing in that directory is edited by
  hand; a new Mica release means new pins and a rerun of the script.
- The copy lives in `Regex::Mica` instead of the top-level `Mica`. An
  application can still require the mica shard, at any version, without
  the two copies reopening each other's classes. The script makes exactly
  two rewrites: `module Mica` becomes `module Regex::Mica`, and the fully
  qualified `::Mica::` becomes `::Regex::Mica::`. Every other reference in
  Mica is relative and resolves the same way inside `Regex`.
- Mica's `static` macro (patterns compiled while the application builds)
  runs helper programs from `src/mica/regex/static/`; those are not
  vendored, so the stdlib engine compiles every pattern at run time, as
  PCRE2 does.
- A program built with `-Duse_pcre2` or `-Duse_pcre` compiles none of the
  vendored engine. The compiler always carries the syntax front half, for
  the literal check described below.

The engine itself is `Regex::MicaEngine` (`src/regex/mica_engine.cr`), the
counterpart of `Regex::PCRE2`; `src/regex/engine.cr` aliases
`Regex::Engine` to it unless `-Duse_pcre2` or `-Duse_pcre` is given.

## How the Regex API maps onto Mica

| `Regex` | Mica |
|---|---|
| `Regex.new(source, options)` | `Mica::Regex::Expression.new(source, options, compile_limits: TRUSTED_PATTERN)` |
| `#match`, `#match_at_byte_index`, `String#match`, `=~`, `$~` | `Expression#search_groups` from the byte index the stdlib computes; the group offsets fill a `Regex::MatchData` exactly as PCRE2's ovector does (begin and end pairs, -1 for a group that did not take part) |
| `#matches?`, `#matches_at_byte_index?` | `Expression#matches_at_byte_index?` |
| `#name_table`, `#capture_count`, named groups, duplicate names | Mica keeps PCRE2's name-table order; `MatchData#[name]` resolves a duplicate name with the same rule as the PCRE2 binding |
| `gsub`, `sub`, `scan`, `split` | unchanged: the stdlib builds them on `match_at_byte_index` |
| `Regex.error?` | compiles the pattern and returns the message, or nil |
| `Regex::Engine.version_number` | `{10, 49}`: Mica reads patterns as PCRE2 10.49 does, so version checks written for PCRE2 see that dialect |

Options:

| Option | Mica |
|---|---|
| `IGNORE_CASE`, `MULTILINE` (multiline + dotall), `MULTILINE_ONLY`, `DOTALL`, `EXTENDED`, `ANCHORED`, `DOLLAR_ENDONLY`, `FIRSTLINE`, `ENDANCHORED` | the Mica option of the same meaning |
| `UTF_8`, `UCP`, `DUPNAMES` | always on |
| `NO_UTF_CHECK` (compile) | invalid UTF-8 in the pattern is read as U+FFFD |
| `NO_UTF_CHECK` (match) | Mica validates every haystack. A haystack with invalid UTF-8 is searched run by run: each run of valid UTF-8 is searched on its own, with one non-word, non-newline character of context before it, so invalid bytes never match and `^`, `\A` and `\b` see the invalid byte as a non-word character. `$` and `\z` can match at the end of a run. (PCRE2 leaves this case undefined.) |
| `MATCH_INVALID_UTF` | not supported: `Regex.supports_compile_options?` returns false and `Regex.new` raises `ArgumentError` (Mica milestone R4) |
| `MatchOptions::NO_JIT` | ignored |

Errors:

| Case | Raises |
|---|---|
| Invalid pattern syntax | `ArgumentError` with Mica's message and byte offset (`"missing closing parenthesis at 8"`; Mica's parser follows PCRE2's rules and offsets) |
| Valid PCRE2 that Mica leaves out | `Regex::UnsupportedSyntaxError`, an `ArgumentError` with `#construct` and `#byte_offset`. It is an `ArgumentError` because `Regex.new` documents `ArgumentError` for every pattern it cannot compile, and code that compiles user patterns rescues that |
| A pattern past the compile limits | `ArgumentError` naming the limit |
| Invalid UTF-8 in the haystack | `ArgumentError` (`"UTF-8 error"`), as with PCRE2 |
| A byte index inside a character | `ArgumentError` (`"bad offset into UTF string"`), as with PCRE2 |
| A search past its work allowance | `Regex::Error`, as PCRE2's match limit |

Compiled patterns are shared: `Regex` values with the same source and
options share one Mica expression (immutable and safe to share between
fibers and threads), and the engine keeps the 256 most recently compiled.
PCRE2 compiles a pattern in microseconds outside the garbage-collected
heap; Mica compiles in Crystal and builds its search plan during the first
searches, so a pattern rebuilt in a loop (`str.gsub(/#{name}:/, ...)`)
would otherwise cost allocations, and garbage collections in a program
with a large heap.

Limits: patterns compile under Mica's `TRUSTED_PATTERN` limits (64 KiB of
pattern, 1,000,000 program states, 64 MiB of Pike VM workspace) and search
under `TRUSTED_INPUT` (an allowance that grows with the haystack and the
program, capped at 10^9 operations per call).

## Literals are checked when the program compiles

A program that runs on Mica has every regex literal checked against
Mica's dialect while the compiler expands it (`MicaRegexLiteral` in the
compiler), so a literal Mica cannot run is a compile error, not an
exception the first time it is used. The error names the way out:

```console
$ crystal build app.cr
Error: invalid regex for the Mica regex engine: lookahead (at 1) is not supported; build with -Duse_pcre2 to run this pattern on PCRE2, or see doc/regex_mica.md for rewrites
$ crystal build -Duse_pcre2 app.cr
```

Only literals the program reaches are checked: a literal in a method that
is never called is never expanded.

The compiler carries Mica's syntax front half for this check whatever
engine it was built with. The parser's own literal check (`invalid regex`)
uses the engine the compiler was built with; a compiler built on Mica
accepts a literal Mica leaves out there, since it is valid PCRE2 and the
program may be built with `-Duse_pcre2`. Patterns built at run time
(`Regex.new`, interpolated literals) raise `Regex::UnsupportedSyntaxError`
when compiled, and its message names `-Duse_pcre2` too.

Macro code runs regexes on the engine the compiler was built with: the
compiler runs `StringLiteral#gsub(/.../)` and the other macro regex
methods on Mica, whatever engine the program selects.

## Syntax Mica does not run

Everything else in PCRE2's syntax is accepted (see Mica's `docs/regex.md`,
"Syntax"). These constructs do not fit an engine whose searches are linear
in the haystack:

| Construct | Rewrite |
|---|---|
| Backreferences `\1`, `\g{n}`, `\k<name>`, `(?P=name)` | Capture both parts and compare them in Crystal |
| Lookahead `(?=` `(?!` and lookbehind `(?<=` `(?<!` | Match the wider text and check the context in Crystal, or capture the context as a group |
| Atomic groups `(?>...)`, possessive quantifiers `a++` | Drop them: the engine never backtracks |
| Recursion and subroutine calls `(?R)`, `(?1)`, `(?&name)` | Use a parser for nested structure |
| Conditional groups `(?(1)...\|...)` | Alternation, or two patterns |
| Callouts and backtracking verbs `(*FAIL)`, `(*SKIP)`, ... | None |
| `\K` | Capture the part after `\K` as a group |
| `\C` | `.` |
| `\X` | Not yet (Mica milestone R9) |
| Newline conventions `(*CR)`, `(*CRLF)`, `(*ANY)`, `(*ANYCRLF)`, `(*NUL)` | Crystal uses LF; match `\r?$` explicitly |

Other differences:

- `MATCH_INVALID_UTF` is not supported (above).
- A pattern whose Pike VM workspace passes 64 MiB is refused at compile
  time; for example 1,000 capture groups each holding `.` (PCRE2 accepts
  it, Mica accepts 300).
- Error messages for invalid syntax follow PCRE2's wording for the common
  cases but are Mica's own.

## Updating the vendored copy

1. Check out the new Mica release tag.
2. Update `PINNED_TAG`, `PINNED_COMMIT` and `PINNED_TREE` in
   `scripts/vendor_mica.cr` from `git rev-parse <tag>^{commit}` and
   `git rev-parse <tag>^{tree}`.
3. `crystal run scripts/vendor_mica.cr -- path/to/mica`
4. `crystal spec spec/std/regex_spec.cr spec/std/regex spec/std/string_spec.cr`,
   and the same with `-Duse_pcre2`.
